## 2. Requirement

The ONX protocol operates on an Actor model where accounts interact exclusively via asynchronous messages. To achieve deterministic execution across sharded networks, the protocol requires:
1. Formal differentiation between **Internal Messages** (account-to-account value transfers and smart contract calls) and **External Inbound Messages** ("messages from nowhere", user-to-account transaction candidates).
2. A deterministic multi-currency value model representing balances and transfers as pairs of `(currency_id, value)`.
3. An **output-queue-only** messaging architecture with explicit partial ordering invariants for message delivery across accounts and shardchains.
4. Deterministic inter-shard routing mechanisms with guaranteed message delivery, bounded transit latency, and explicit ordering rules.
5. Strict double-delivery and replay prevention semantics across all shardchains.
6. Unambiguous malformed-input rejection rules for invalid message formats, unauthorized external transactions, and routing inconsistencies.

## 3. ONX Interpretation

### 3.1 Message Types & Admission Rules
1. **Internal Messages (`msg_type = 0x01`):**
   - Sent by an account (smart contract or wallet) to another account within the same or different shardchains.
   - **Value Bearing:** Internal messages carry principal Onyx currency (`amount_nanos`) and optionally additional tokens (`extra_currencies`).
   - **Fee Deductions:** Gas and forwarding fees are deducted directly from the attached message value or originating account balance.
   - **Admission Rule:** Admitted if generated during valid execution of a prior message or transaction on an Active account.

2. **External Inbound Messages (`msg_type = 0x02`):**
   - Sent from an off-chain actor ("from nowhere") to an account in the blockchain (e.g. user initiating a transaction).
   - **Zero Value:** External messages carry zero value (`amount_nanos = 0` and empty `extra_currencies`) and cannot pay gas upfront.
   - **Tentative Execution Admission Rule:** To prevent DoS attacks, collators/validators MUST tentatively execute external messages under a strict, small gas limit (e.g., `MAX_TENTATIVE_GAS = 10,000`) against the target account's current state prior to block inclusion.
     - If signature verification or initial state validation fails during tentative execution, the message is discarded immediately.
     - If tentative execution succeeds, the message is admitted into the block candidate; total transaction gas fees and storage fees are deducted from the recipient account's balance upon full execution.

3. **External Outbound Messages (`msg_type = 0x03`):**
   - Generated by smart contracts to log events or emit off-chain notifications ("messages to nowhere"). They are included in block output logs but are not routed to any recipient account state.

### 3.2 Value Model & `extra_currencies` Integration
1. **Principal Currency (`currency_id = 0`):** Represented as a 128-bit big-endian unsigned integer (`amount_nanos`) tracking nanotons ($10^{-9}$ Onyx coins).
2. **Extra Currencies (`extra_currencies`):**
   - Additional custom cryptocurrencies or tokens are represented as a dictionary/hashmap of `(currency_id, value)` pairs where `currency_id` is a 32-bit unsigned integer (`uint32`) and `value` is a 128-bit unsigned integer (`uint128`).
   - In `docs/specification/data-structures.md` §4.3, `extra_currencies` is serialized as a count-prefixed array of `(currency_id, value)` pairs sorted in strictly ascending order by `currency_id`.
   - The total balance of an account and the value carried by an internal message MUST explicitly track `amount_nanos` plus any non-zero `extra_currencies`.

### 3.3 Output-Queue-Only Architecture & Delivery Ordering
1. **Absence of Input Queues (§2.4.16):**
   - Shardchains do not maintain persistent input message queues. Inbound messages included in a block are executed immediately.
   - If block gas limits or byte limits prevent processing all candidate messages, undelivered messages remain in the originating shardchain's **Output Queue**.
2. **Shardchain Output Queue (`out_queue` §2.4.17):**
   - Each shardchain state contains an authenticated hashmap/trie representing the union of output message queues for all accounts belonging to that shard.
   - **Partial Delivery Order Invariants:**
     1. **Logical Time / Block Order:** Messages generated in a block with lower logical time / block height MUST be processed before messages generated in subsequent blocks.
     2. **FIFO per Sender-Recipient Pair:** For messages generated by the same sender account $A$ to the same destination account $B$, delivery MUST preserve the exact generation sequence order ($lt_1 < lt_2 \implies$ delivered $lt_1$ before $lt_2$).

### 3.4 Inter-Shard Routing: Hypercube Routing & Fast Path
1. **Mandatory Hypercube Routing ("Slow Path" §2.4.19):**
   - ONX adopts mandatory hypercube routing across shardchains.
   - Shardchains are organized as vertices in a hypercube graph based on hexadecimal or binary prefixes of `ShardIdent`. A shard $(w, s)$ is connected directly to neighboring shards differing in exactly one digit/bit position.
   - Inter-shard messages traverse intermediate neighboring shardchains step-by-step. At each transit hop, a forwarding transaction consumes a small forwarding gas fee from the message value and enqueues the message into the transit shard's output queue.
   - Hypercube routing provides failproof, guaranteed message delivery without requiring validators to monitor all non-neighboring shard states.
2. **Fast Path / Instant Hypercube Routing (§2.4.20 - ONX Decision):**
   - **Deferred in Baseline Protocol:** Instant Hypercube Routing ("fast path" direct relay with off-chain Merkle proofs) is **deferred** for initial ONX protocol deployment to reduce BFT consensus complexity and validator state tracking overhead (assigned to **ONX-ARCH-011**).
   - All inter-shard messages in initial ONX releases MUST follow standard, deterministic hypercube routing along neighboring shard boundaries.

### 3.5 Double-Delivery Prevention
1. **Delivered Message Hash Tracker (`processed_msg_hashes` §2.4.23):**
   - Each account state or shardchain state maintains a set/hashmap of recently delivered message representation hashes (`SHA256(Message)`).
   - When an inbound message is admitted for execution, its representation hash is checked against `processed_msg_hashes`. If present, the message MUST be rejected as a duplicate.
   - Upon successful execution, the message hash is added to `processed_msg_hashes`.
2. **Pruning & Garbage Collection:**
   - When an originating neighboring shard removes a delivered message from its output queue (confirmed via masterchain block reference), transit and recipient shards prune the message hash from `processed_msg_hashes`.

## 4. Serialization

### 4.1 Message Binary Layout
Consensus binary layout for `Message` (conforming to `docs/specification/data-structures.md` §4.3):
```
1. msg_type         : uint8   (0x01 = Internal, 0x02 = External Inbound, 0x03 = External Outbound)
2. src_address      : FullAddress (36 bytes: workchain_id int32 + account_id uint256)
3. dest_address     : FullAddress (36 bytes: workchain_id int32 + account_id uint256)
4. amount_nanos     : uint128 (16 bytes, big-endian)
5. extra_curr_count : uint32  (4 bytes, count of extra currency pairs)
6. extra_currencies : [ExtraCurrencyPair; extra_curr_count]
7. created_lt       : uint64  (8 bytes, logical time of message creation)
8. body_cell_hash   : uint256 (32 bytes, SHA-256 digest of payload cell tree)
```

### 4.2 Extra Currency Pair Layout (`ExtraCurrencyPair`)
```
1. currency_id : uint32  (4 bytes, big-endian)
2. value       : uint128 (16 bytes, big-endian)
```

### 4.3 Domain-Separated Message Hashing
The canonical representation hash $H(\text{Message})$ is computed as:
$$\text{MsgHash} = \text{SHA256}(\text{ONX:MSG:HASH:V1} \parallel \text{serialized\_message\_bytes})$$
Where `ONX:MSG:HASH:V1` is the 32-byte domain separation tag `ONX_MSG_HASH_V1\x00...` (padded with zeros to 32 bytes).

## 5. Malformed-input behavior

Consensus validation modules and transaction execution engines MUST immediately reject a message or block candidate if:
1. **Invalid Message Type:** `msg_type` is not in `{0x01, 0x02, 0x03}`.
2. **Non-Zero External Value:** An External Inbound message (`msg_type = 0x02`) specifies `amount_nanos > 0` or non-empty `extra_currencies`.
3. **Tentative Execution Failure:** An External Inbound message fails signature verification or exceeds `MAX_TENTATIVE_GAS` during preliminary evaluation.
4. **Unsorted Extra Currencies:** `extra_currencies` contains duplicate `currency_id` keys or pairs that are not in strictly ascending `currency_id` numerical order.
5. **Double Delivery Attempt:** An inbound message representation hash already exists in the destination account's `processed_msg_hashes` set.
6. **Order Violation:** Messages selected from an output queue violate FIFO order for the same `(src_address, dest_address)` pair or violate logical time monotonicity ($lt_{\text{msg}} > lt_{\text{block}}$).
7. **Hypercube Routing Violation:** An inter-shard message is routed to a destination shard that is not a valid hypercube neighbor or final destination for the message step.
8. **Value Insufficiency:** An internal message value `amount_nanos` is insufficient to cover the required hypercube transit forwarding fee.

## 6. Test plan

1. **Message Serialization & Multi-Currency Tests:**
   - Round-trip serialization tests for Internal, External Inbound, and External Outbound messages.
   - Verification of `extra_currencies` sorting enforcement and rejection of unsorted/duplicate currency IDs.
   - Domain-separated message hashing verification against `ONX_MSG_HASH_V1`.
2. **External Message Admission & Tentative Execution Tests:**
   - Test tentative execution of valid external messages under `MAX_TENTATIVE_GAS`.
   - Test immediate rejection of external messages with invalid cryptographic signatures or non-zero value payloads.
3. **Output Queue Ordering & FIFO Invariant Tests:**
   - Verification of FIFO delivery order enforcement for messages from single sender to single recipient.
   - Rejection tests for out-of-order message selection or logical time regression.
4. **Hypercube Routing Tests:**
   - Verification of step-by-step hypercube path calculation across 2D, 3D, and 4D shard hypercubes.
   - Rejection of invalid transit steps that jump non-neighboring hypercube dimensions.
5. **Double-Delivery Prevention Tests:**
   - Verification that processed message hashes are correctly added to `processed_msg_hashes`.
   - Negative tests confirming immediate rejection when attempting to re-deliver a previously executed message hash.
