## 2. Requirement

The protocol specification requires explicit, deterministic rules for:
1. Derivation and verification of **256-bit abstract network addresses** from serialized key descriptions (preimages).
2. The **low-level transport binding** over UDP (with TCP fallback) and the wire encodings for encrypted datagrams (both full public-key encrypted packets and ECDH shared-secret packets with nonces).
3. The multiplexing and handling of **channel identifiers**, **tunnel identifiers** for onion/garlic proxy routing, and the **zero-channel** (`0x00...00`) for light-client bootstrapping.
4. The packet structure, Forward Error Correction (FEC) chunking, acknowledgement mechanics, and loss recovery rules for the **Reliable Large Datagram Protocol (RLDP)** operating over ADNL.
5. Strict, deterministic **malformed-input rejection rules** to prevent invalid datagrams, replay attacks, or corrupted network frames from affecting node operations.

## 3. ONX Interpretation

### 3.1 Abstract Network Addresses and Key Descriptions

- An **abstract network address** (or *abstract address*) is a 256-bit (`uint256`) identifier assigned to a network entity.
- An abstract address is computed strictly as the SHA-256 hash of a canonical serialized TL-object called the **key description** (or *preimage*):
  $$\text{abstract\_address} = \text{SHA-256}(\text{key\_description})$$
- The key description explicitly identifies the public-key algorithm, key parameters, and public key material. The default key description scheme uses Ed25519 (32-byte public key). Alternative schemes (such as RSA-2048 or multi-key structures) are identified by distinct 4-byte TL constructor tags.
- To encrypt and route datagrams to a target abstract address, a sender MUST possess both the 256-bit abstract address and its matching preimage (key description).
- A node receiving a datagram for an abstract address must possess the corresponding private key to decrypt and verify the payload.

### 3.2 Transport Protocols and Packet Encodings

ADNL operates primarily over UDP (IPv4 and IPv6). Nodes MAY fall back to TCP if UDP is blocked by local network configurations. Every UDP packet carrying an ADNL frame begins with a 256-bit (`32`-byte) **channel identifier** or destination address prefix.

ADNL defines two primary transport packet encodings:

1. **Full Public-Key Encrypted Packet (§3.1.3):**
   - The first 32 bytes contain the recipient's 256-bit abstract address.
   - The remainder of the payload is encrypted using the recipient's public key (retrieved from the key description).
   - The decrypted payload contains the sender's source abstract address (and key description preimage if not previously exchanged), an Ed25519 digital signature generated by the sender's private key, a timestamp/nonce to prevent replay, and the datagram payload.
   - *Privacy Property:* Sender identity is hidden from external eavesdroppers and revealed only after successful recipient decryption.

2. **Shared-Secret / Fast Channel Encrypted Packet (§3.1.4):**
   - Used when peers establish repeated communication.
   - The unencrypted header contains the recipient abstract address, sender abstract address, and a random 256-bit (`32`-byte) nonce.
   - A shared secret $S$ is derived once via Elliptic Curve Diffie-Hellman (ECDH) between the sender's private key and recipient's public key.
   - Symmetric key material is derived using SHA-256 over $S \parallel \text{nonce}$.
   - The payload is encrypted with AES-256-CTR. Integrity is verified via SHA-256 appended to the plaintext payload prior to encryption.
   - *Performance Property:* ECDH key agreement is cached; subsequent datagrams require only fast AES-256 symmetric decryption.

### 3.3 Channel Identifiers, Tunneling, and Bootstrapping

- **Point-to-Point Channel Identifiers (§3.1.5):** Two peers exchanging large volumes of traffic establish a point-to-point channel. A 256-bit channel ID is derived as:
  $$\text{channel\_id} = \text{SHA-256}(\text{shared\_secret} \parallel \text{sender\_address} \parallel \text{recipient\_address})$$
  When a UDP packet's first 32 bytes match an active channel ID, the recipient processes the payload directly using the cached symmetric channel keys.
- **Tunnel Identifiers and Proxy Routing (§3.1.6):** Channel identifiers can represent multi-hop tunnel routes. Intermediate proxy nodes inspect the channel ID, decrypt/re-encrypt layer wrappers (garlic/onion routing), and forward the datagram to the next tunnel hop without inspecting inner payloads. This provides the transport foundation for ONX Proxy (`WHITEPAPER.md` §4.1.10).
- **Zero-Channel Bootstrapping (§3.1.7):**
  - Reserved channel ID $0\times0000...0000$ (32 zero bytes).
  - Used when a client or bootstrapping node knows a target's IP address and UDP port but does not yet know its abstract address or key description (e.g. initial network boot).
  - Datagrams sent over the zero-channel are unencrypted at the channel layer but MUST contain the sender's public key description, timestamp, signature, and query payload.
  - Zero-channel datagrams are strictly restricted to peer key-exchange and bootstrap queries; general application datagrams over the zero-channel MUST be rejected.

### 3.4 Reliable Large Datagram Protocol (RLDP)

ADNL provides unreliable, un-ordered datagram delivery. The **Reliable Large Datagram Protocol (RLDP)** operates directly on top of ADNL to transfer arbitrary-sized messages (e.g., RPC queries, block transfers, large state snapshots):

1. **Segmentation and FEC Chunking:** Large messages are partitioned into data chunks of fixed size (default $1024$ bytes). The chunk sequence is augmented using Forward Error Correction (FEC) fountain codes (RaptorQ / Reed-Solomon style) to generate repair symbols.
2. **Transmission & Reconstruction:** The sender streams data and FEC repair chunks over ADNL datagrams. The recipient collects incoming chunks; once any $N$ distinct valid chunks are received (where $N$ is the original payload chunk count), the full message is reconstructed.
3. **Acknowledgements (ACK) & Loss Recovery:** Upon successful reconstruction, the recipient sends an explicit RLDP ACK frame back to the sender, instructing it to cease emitting repair chunks.
4. **RPC Encodings:** RLDP payloads standardize Remote Procedure Call (RPC) request/response frames carrying TL-serialized query structures and request nonces for response matching.

## 4. Serialization

All ADNL and RLDP data structures are serialized in big-endian byte order, aligned with `protocol-primitives.md`.

### 4.1 Key Description Serialization

```
KeyDescription:
  1. constructor_tag : uint32  (0x48a30121 for Ed25519)
  2. public_key      : uint256 (32 bytes Ed25519 public key)
```

`abstract_address` = `SHA-256(KeyDescription)` (32 bytes).

### 4.2 ADNL Transport Packet Headers

#### 4.2.1 Full Public-Key Encrypted Packet
```
FullPacketHeader:
  1. recipient_address : uint256 (32 bytes)
  2. encrypted_payload : bytes   (variable length)

Decrypted Payload Layout:
  1. sender_address    : uint256 (32 bytes)
  2. timestamp         : uint32  (UNIX Epoch seconds)
  3. nonce             : uint32  (random replay guard)
  4. payload_len       : uint16
  5. payload           : bytes   (payload_len bytes)
  6. signature         : bytes   (64 bytes Ed25519 signature over items 1..5)
```

#### 4.2.2 Shared-Secret / Fast Encrypted Packet
```
FastPacketHeader:
  1. recipient_address : uint256 (32 bytes)
  2. sender_address    : uint256 (32 bytes)
  3. nonce             : uint256 (32 bytes)
  4. encrypted_payload : bytes   (AES-256-CTR encrypted)

Plaintext Payload (prior to AES encryption):
  1. payload_hash      : uint256 (SHA-256 digest of payload_data)
  2. payload_len       : uint16
  3. payload_data      : bytes   (payload_len bytes)
```

#### 4.2.3 Zero-Channel Packet
```
ZeroChannelPacket:
  1. channel_id        : uint256 (must be all zeroes: 0x00...00)
  2. sender_key_desc   : KeyDescription
  3. timestamp         : uint32
  4. nonce             : uint32
  5. payload_len       : uint16
  6. payload           : bytes
  7. signature         : bytes   (64 bytes Ed25519 signature over items 1..6)
```

### 4.3 RLDP Frame Formats

```
RLDPMessageFrame:
  1. rldp_tag          : uint32  (0x71d2b841 for RLDP Data Chunk)
  2. transfer_id       : uint256 (32 bytes unique transfer nonce)
  3. total_size        : uint32  (total uncompressed message size in bytes)
  4. chunk_size        : uint16  (payload bytes per chunk, default 1024)
  5. chunk_count       : uint16  (total original chunks N)
  6. seq_no            : uint16  (chunk sequence index, 0..N-1 for data, >=N for FEC)
  7. chunk_data        : bytes   (chunk_size bytes)

RLDPAckFrame:
  1. rldp_tag          : uint32  (0x3a4f1092 for RLDP ACK)
  2. transfer_id       : uint256 (32 bytes unique transfer nonce)
  3. received_mask     : bytes   (bitmask or count of received chunks)
```

## 5. Malformed-input behavior

Nodes MUST reject and drop incoming ADNL or RLDP network datagrams immediately if any of the following occur:

1. **Truncated Packet:** Packet size is smaller than the minimum header size for the indicated packet type (e.g. fewer than 32 bytes for recipient address or channel ID).
2. **Abstract Address / Preimage Mismatch:** The SHA-256 hash of a provided key description preimage does not equal the expected 256-bit abstract address.
3. **Decryption / Integrity Failure:** AES-256 payload decryption yields an invalid `payload_hash` SHA-256 digest, or public-key decryption fails.
4. **Invalid Signature:** Ed25519 signature verification fails on a full public-key or zero-channel packet.
5. **Expired or Replayed Timestamp:** The timestamp in a packet header differs from local node system time by more than $60$ seconds, or a `nonce` is matched in the recent anti-replay cache.
6. **Zero-Channel Abuse:** Non-bootstrap application payload transmitted over the zero-channel (`channel_id = 0x00...00`).
7. **Malformed RLDP Frame:** `chunk_size` exceeds $65,535$ bytes, `chunk_count` is $0$, or payload size in an RLDP chunk does not match declared `chunk_size`.
8. **Excessive RLDP Transfer Size:** `total_size` in an RLDP frame exceeds maximum allowed node datagram size limits (default $16$ MB).

## 6. Test plan

1. **Abstract Address Derivation Tests:**
   - Verify SHA-256 address derivation from valid Ed25519 key descriptions.
   - Verify rejection of invalid constructor tags or malformed key description preimages.
2. **Transport Encrypt / Decrypt Tests:**
   - Round-trip public-key encryption and decryption between two test keypairs.
   - Verify ECDH shared-secret derivation, AES-256-CTR key generation, and packet decryption.
   - Test anti-tamper rejection when payload bytes or `payload_hash` digests are altered.
3. **Channel & Tunnel ID Unit Tests:**
   - Verify channel ID derivation for point-to-point peer channels.
   - Test zero-channel packet parsing, signature verification, and non-bootstrap payload rejection.
4. **RLDP Chunking & FEC Reconstruction Tests:**
   - Test fragmentation of large payloads into 1024-byte chunks.
   - Test FEC reconstruction when $10\%$, $20\%$, or $30\%$ of random chunks are dropped.
   - Test RLDP ACK generation and cease of transmission upon completion.
5. **Adversarial Network Tests:**
   - Replay test: inject identical nonces and verify rejection by the timestamp/nonce anti-replay filter.
   - Truncated frame injection test: verify robust dropping without panic or memory allocation failure.
